* Purpose and scope
This document is the canonical description of how memory is allocated, owned,
and released in Blade. It covers:
- All allocators currently used at runtime and in tests
- The lifetime rules tied to each allocator
- The ownership flow between the producer thread and the UI thread
- Per-batch vs long-lived data structures in AppState
- Scratch allocation usage and what must never escape
- Pitfalls and invariants that keep the system correct

If you only read one thing, read the *Allocator Inventory* and *Ownership
Invariants* sections.

* Terminology (allocator vocabulary)
We use the same three-way split described in docs/designPatterns.org:
- gpa: long-lived allocations, explicitly freed or deinit on shutdown.
- arena: batch-scoped allocations, released in one deinit.
- scratch: temporary allocations inside a function, never returned or stored.

Additionally:
- page_allocator: OS page allocator used as the backing allocator for arenas.
- testing allocator: std.testing.allocator used only in test blocks.

* High-level memory flow (data thread to UI thread)
#+BEGIN_EXAMPLE
Process data flow (ownership and allocators)

  [Producer Thread]                                     [UI Thread]

  page_allocator
       |
       v
  ArenaAllocator (batch.arena)  -----> BatchQueue (gpa) -----> AppState
       |                                 (transfers Batch)        |
       |                                                          |
       v                                                          v
  AutoHashMap(pid -> *Proc)                              current_batch + previous_batch
  Proc structs, PID list, etc.                           hot/cold arrays (gpa)

Key idea: all snapshot data lives in one arena per batch.
The queue only moves the Batch struct (small, by value).
#+END_EXAMPLE

* Detailed ownership and lifetime timeline
#+BEGIN_EXAMPLE
Batch lifetime timeline (one refresh cycle)

Time --->

Producer:
  t0: create batch_arena (page_allocator)
  t1: collectSnapshot(arena) -> raw_map (arena)
  t2: allocate Proc objects in arena, fill batch.map (arena)
  t3: push Batch into queue (ownership transfers)

Consumer (UI):
  t4: pop Batch, set AppState.current_batch
  t5: buildView() uses current_batch to fill hot/cold/index arrays
  t6: render frame(s) using hot/cold slices
  t7: on next batch arrival:
      - previous_batch.deinit() (if present)
      - previous_batch = current_batch
      - current_batch = new_batch

Memory retention window: up to TWO arenas at once (current + previous).
#+END_EXAMPLE

* Allocator contracts (rules of the road)
** gpa (GeneralPurposeAllocator)
- Used for long-lived application state and reusable buffers.
- Explicitly freed in AppState.deinit or during batch refresh where needed.
- Examples:
  - AppState.hot / AppState.cold storage
  - AppState.indices / AppState.sorted_indices
  - AppState.expanded_pids
  - Lowercased strings for search (name_lower, path_lower)
  - Queue backing storage (BatchQueue.initCapacity)
  - zigtui backend + terminal (external library)

Contract: Anything allocated from gpa must be freed or deinit when no longer
needed. Most gpa allocations are retained and reused to avoid churn.

** arena (std.heap.ArenaAllocator)
- Used for per-batch snapshots in the producer thread.
- Freed in one shot by calling batch.arena.deinit().
- All map entries and Proc structs are allocated inside this arena.
- The arena is backed by std.heap.page_allocator for fast, bulk allocation.

Contract: No references to arena-allocated data may escape the batch lifetime.
If a slice or pointer outlives the batch, it is a bug.

** scratch (temporary, function-scoped)
- Used for short-lived computation buffers.
- Currently DrawContext.scratch is gpa_alloc (so scratch is still gpa), but it
  is treated as scratch by contract.
- Example: ui/layout.calculate uses scratch to build a StringHashMap of rects.

Contract: Never return or store scratch-allocated memory in AppState or any
long-lived structure. Call deinit on any container allocated with scratch.

** page_allocator (OS pages)
- Not used directly for application data.
- Backing allocator for arenas.

Contract: Always wrap with ArenaAllocator for batch data; do not allocate
per-Proc with page_allocator directly.

** testing allocator (std.testing.allocator)
- Used only in test blocks for ui/layout.
- Not part of runtime memory flow.

* Where allocations happen (by file / subsystem)
** src/main.zig
- Creates gpa_alloc (GeneralPurposeAllocator).
- Initializes:
  - zigtui backend and terminal with gpa_alloc
  - AppState with gpa_alloc
  - BatchQueue with gpa_alloc
- Passes gpa_alloc as DrawContext.scratch each frame.

Lifetime summary:
- gpa_alloc: entire program
- queue: entire program
- AppState: entire program

** src/thread/producer.zig (producer thread)
Key allocations:
- batch_arena = ArenaAllocator.init(page_allocator)
- batch.map = AutoHashMap(...).init(arena_alloc)
- raw_map = platform.collectSnapshot(arena_alloc)
- For each process: arena_alloc.create(Proc)

Important detail:
- raw_map is arena-allocated and not deinit'ed. This is correct because
  batch_arena.deinit() will free everything in one shot.

** src/thread/channel.zig (Batch type and queue)
Batch layout:
- batch.arena: ArenaAllocator
- batch.map: AutoHashMap(pid_t, *Proc)
- batch.timestamp_ns: i128

Deinit behavior:
- batch.deinit() calls ONLY arena.deinit().
- map.deinit() is intentionally omitted because the Allocator captured by
  map.init() points to the producer's stack arena instance (see comment in code).
  Calling map.deinit() would dereference a stale allocator pointer.

Invariant:
- The arena must be deinitialized exactly once by the owner (consumer).
- Do not call map.deinit() unless the allocator is proven safe to use.

** src/platform/macos.zig
- collectSnapshot(arena) allocates:
  - pids array with arena.alloc
  - AutoHashMap(pid_t, Proc) using the arena allocator
- Proc.toSnapshop(arena) duplicates name/path into arena-owned slices.

Notes:
- The macOS implementation returns a value map (Proc by value), then the
  producer copies values into arena-allocated Proc pointers.
- Linux/Windows currently return error.Unsupported (no runtime allocations).

** src/state.zig (AppState and view)
Long-lived (gpa) allocations:
- hot: MultiArrayList(ProcHot)
- cold: ArrayList(ProcCold)
- indices: ArrayList(usize)
- sorted_indices: ArrayList(usize)
- expanded_pids: AutoHashMap(pid_t, void)

Per-batch allocations that are freed/replaced:
- name_lower, path_lower: gpa.alloc per item per refresh

Important cross-lifetime references:
- ProcCold.name and ProcCold.path are slices into the current batch's Proc
  structs (arena memory). These slices are only valid while current_batch
  is alive.
- AppState keeps previous_batch for CPU delta computation; this means two
  arenas can be alive at the same time.

** src/ui/layout.zig
- calculate(scratch, ...) creates a StringHashMap(Rect) using the scratch allocator.
- CalculatedLayout.deinit() must be called by the caller to free the map.

Tests:
- layout tests use std.testing.allocator explicitly.

* Memory model by subsystem (who owns what)
** Producer thread
Owns (temporarily):
- batch.arena
- raw_map (arena)
- batch.map (arena)

Transfers ownership of:
- Batch (arena + map + timestamp) to the queue

** BatchQueue (SPSC queue)
Owns (long-lived):
- Queue backing memory (gpa)

Transfers ownership of:
- Batch instances to consumer

** UI thread / AppState
Owns (long-lived):
- AppState hot/cold buffers (gpa)
- Search buffers, indices, expanded_pids (gpa)
- Terminal/backend (gpa)

Owns (batch-scoped):
- current_batch (arena)
- previous_batch (arena)

Uses (scratch):
- DrawContext.scratch (currently gpa, treated as scratch)

* Data structure notes and lifetime subtleties
** ProcCold slices and batch lifetime
ProcCold stores:
- name: slice into Proc.s_name (arena)
- path: slice into Proc.path (arena)
- name_lower: gpa allocation (lowercased copy)
- path_lower: gpa allocation (lowercased copy)

Implication:
- name/path are invalid after current_batch is deinit.
- name_lower/path_lower must be freed when cold list is rebuilt.
- hot/cold arrays can be reused; the slices they contain must not outlive
  the batch that provided them.

** previous_batch retention (CPU delta)
AppState keeps previous_batch so it can compute CPU percentage by comparing
process cumulative CPU times between snapshots. This doubles arena memory
transiently:
- current_batch (new data)
- previous_batch (last data)

Rule:
- previous_batch is deinit'ed on receipt of the next batch.

** Reserve-first and index indirection
The view pipeline uses reserve-first patterns when building indices:
- ensureTotalCapacity(...) then appendAssumeCapacity

The project prefers indices over pointers for long-lived references. When
indexing data from the batch, the AppState keeps indices into its own arrays
(not into the arena). This avoids retaining direct pointers into arenas.

  +---------------------------------------+
  | arena: ArenaAllocator (page_allocator) |

#+END_EXAMPLE

* Ownership invariants (must never be violated)
1) Never store references to arena data outside a batch lifetime.
   - This includes slices to Proc.s_name/path and pointers to Proc structs.
2) The UI thread is the sole owner of batch.deinit().
   - Producer must not deinit after pushing to queue.
3) Never call batch.map.deinit().
   - The allocator pointer captured at map.init() can be stale.
4) Scratch allocations must not escape.
   - No scratch data in AppState, global state, or structs stored in gpa.
5) Free gpa allocations tied to a batch refresh.
   - name_lower/path_lower are freed before repopulating cold.
6) Retain no more than two batches at once.
   - current_batch + previous_batch only.

* Practical usage patterns (with examples)
** Per-batch allocation (arena)
#+BEGIN_SRC zig
// producer thread
var batch_arena = std.heap.ArenaAllocator.init(std.heap.page_allocator);
const arena_alloc = batch_arena.allocator();
var batch = channel.Batch{
    .arena = batch_arena,
    .map = std.AutoHashMap(pid_t, *Proc).init(arena_alloc),
    .timestamp_ns = std.time.nanoTimestamp(),
};

// Allocate all proc data in arena
const p = try arena_alloc.create(Proc);
#+END_SRC

** Long-lived allocation (gpa)
#+BEGIN_SRC zig
// AppState init
pub fn init(gpa: std.mem.Allocator) AppState {
    return .{
        .gpa = gpa,
        .expanded_pids = std.AutoHashMap(pid_t, void).init(gpa),
    };
}
#+END_SRC

** Scratch usage
#+BEGIN_SRC zig
// UI layout calculation uses scratch allocator
const ctx = state.DrawContext{ .state = &app, .scratch = gpa_alloc };
// calculate(...) returns a layout; caller must call deinit on the layout
#+END_SRC

* Known pitfalls and how to avoid them
- Storing pointers to Proc or slices to Proc fields in gpa-owned structures
  without guaranteeing the batch lifetime will cause use-after-free.
- Accidentally calling batch.map.deinit() will dereference a stale allocator
  pointer because the Allocator captured the producer's stack arena instance.
- Returning scratch memory (or storing it in AppState) violates the scratch
  contract and can create leaks or invalid memory reads.
- Forgetting to free name_lower/path_lower each batch will leak gpa memory.
- Allocating per-process items directly from gpa in the producer will defeat
  the batch design and create unbounded lifetime allocations.

* How to choose an allocator for new code
Ask these questions in order:
1) Does the data live only for one snapshot/batch?
   - Yes -> arena (batch.arena).
2) Does the data live across batches or for the entire program?
   - Yes -> gpa.
3) Is the data only needed while computing a result?
   - Yes -> scratch (caller-provided temporary allocator).
4) Does the data need to be shared across threads?
   - If shared, do not use scratch; use gpa or a batch with explicit ownership.

Rule of thumb:
- batch -> arena
- app state -> gpa
- per-call -> scratch

* Planned or implied memory work (from docs/tree.org)
Tree view plans (future or in-progress) follow the same allocator rules:
- Per-batch arrays for adjacency and visibility lists should be arena-backed.
- Long-lived UI state like expanded_pids is gpa-backed.
- Reserve-first pattern should be used for adjacency buffers.

This aligns with the documented plan:
- gpa for long-lived state
- arena for per-batch data
- scratch for temporary work buffers

* Checklist for reviewers (memory focused)
- [ ] New pointers/slices are backed by a clear lifetime.
- [ ] Any gpa allocations have a matching free/deinit path.
- [ ] Any arena allocations do not escape the batch.
- [ ] No map.deinit on batch.map.
- [ ] Scratch allocations are deinit'ed and not persisted.
- [ ] Two-batch retention is respected.

* Appendix: Quick reference
** Allocator cheat sheet
- gpa
  - AppState, queues, UI, long-lived buffers
  - Freed in AppState.deinit or at program exit

- arena (batch.arena)
  - Snapshot data (Proc structs, maps, PID list)
  - Freed on batch.deinit (consumer owns)

- scratch
  - Temporary computation (layout, transient buffers)
  - Freed by container deinit; must not escape

- page_allocator
  - Backing storage for arenas

- std.testing.allocator
  - Tests only
